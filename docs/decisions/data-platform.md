# 데이터와 인증 플랫폼

## Decisions

- 물건별 관리 이력, 민원, 사용자와 프로필은 Supabase(Postgres와 Auth)에 저장한다. 이력 관리 DB를 따로 두지 않는다.
- 로그인은 이메일과 비밀번호이고, 이메일 확인은 끈 상태로 운영한다.
- 사용자 정보와 역할은 Auth 사용자와 1:1인 `profiles`에 둔다. 임차인이 기본이고, 임대인은 관리자가 지정한다. 화면에서 스스로 역할을 올릴 수 없다.
- 테이블은 RLS를 켜고, 읽기와 쓰기는 소유자와 역할 기준의 정책으로 연다. 인증 판단은 서버에서 서명이 검증된 claims로만 한다.
- 브라우저에 두는 키는 publishable key뿐이다. secret key와 service-role key는 클라이언트 코드와 저장소에 넣지 않는다.

## Boundaries

- 분류에 쓰는 AI 모델과 임시 분류기는 이 결정의 대상이 아니다. 분류 결과의 모양만 저장 구조의 제약이다.
- 예비 임차인의 접근 요청과 임대인 승인, 물건과 소유 관계는 아직 정하지 않았다. 이 결정은 그 방식을 제한하지 않는다.

## Why

이력은 장기적으로 쌓여 거래 판단에 쓰이므로 처음부터 실제 DB에 두는 편이 나중에 옮기는 비용보다 작다. Supabase는 DB와 Auth와 행 단위 접근 제어를 한곳에서 제공해 소유자 기준 격리를 앱 코드가 아닌 DB 정책으로 지킬 수 있다. 로컬 파일 저장은 시작이 가벼웠지만 이력 단계에서 옮겨야 해서 택하지 않았다.

## Reconsider when

- 물건 단위 소유 관계나 예비 임차인 접근 요청이 RLS 정책만으로 표현되지 않을 때
- 무료 한도나 가용성이 검증에 반복해서 제한이 될 때

## Still-rejected alternatives

- 로컬 파일이나 내장 DB에 먼저 저장 — 이력 단계에서 저장소를 옮겨야 하고 접근 제어를 다시 만들어야 한다. 접수 데이터가 외부 DB에 쌓일 필요가 사라질 때 다시 본다.
- 가입 때 사용자가 역할을 고르는 방식 — 누구나 임대인이 되어 남의 민원을 읽는다. 소유 관계를 검증하는 수단이 생기면 다시 본다.
