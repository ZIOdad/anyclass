# 민원 접수와 자동 분류 (첫 슬라이스)

## 사용자 결과

로그인한 **임차인**이 카테고리를 고르지 않고 자연어로 **민원**을 적어 보내면, 서비스가 **분류 결과**(문제 유형·긴급도·대상 시설)를 붙여 접수하고 임차인에게 그 결과를 보여준다. 로그인한 **임대인**은 접수된 민원을 긴급도 순 목록에서 열어 원문과 분류 결과를 바로 확인한다.

이 슬라이스가 검증하려는 가설은 "임차인이 카테고리를 고르지 않아도 AI가 문제 유형·긴급도·대상 시설을 적절히 분류하고, 임대인이 바로 확인할 수 있는가"이다. 첫 구현은 **임시 분류기**로 만들어 이 흐름이 끝까지 도는지를 보고, 분류 품질은 AI 모델로 바꾼 뒤 사용자가 제공하는 검증 데이터로 판단한다. 따라서 이 슬라이스가 끝나도 "AI 분류가 적절한가"는 아직 검증된 것이 아니다.

용어는 [GLOSSARY.md](../../../GLOSSARY.md)를 따른다.

## 이 작업이 따르는 출처

- [PRODUCT.md](../../../PRODUCT.md): 앱 전체의 제품 전제. 이 슬라이스에는 "신고 내용과 처리자 기록을 구분해 저장", "책임·과실·보상 판정 안 함", "임차인은 쉬운 말로 신고"를 적용한다. 파일은 바꾸지 않는다.
- [docs/decisions/data-platform.md](../../decisions/data-platform.md): 데이터·인증 플랫폼, 역할, 접근 제어, 키 사용 방식을 정한다. 이 슬라이스의 저장과 접근은 이 결정을 따른다.
- [docs/decisions/ui-composition.md](../../decisions/ui-composition.md): 화면 구성과 상태 표현(loading·empty·error·success)을 정한다.

## 정상 흐름

1. 임차인이 로그인한다. 가입한 계정은 기본이 임차인이다.
2. 접수 화면에서 문제를 자연어로 적는다. 카테고리를 고르는 입력은 없다.
3. 제출하면 원문이 먼저 저장되고, 이어서 분류 결과가 붙는다.
4. 임차인은 "이렇게 접수되었습니다"와 함께 문제 유형, 긴급도, 대상 시설을 본다. 임시 분류기가 만든 결과임이 화면에 드러난다.
5. 임대인이 로그인해 임대인 확인 화면을 연다. 접수된 민원이 긴급도 순(같은 긴급도에서는 최근 접수 순)으로 보인다.
6. 임대인이 한 건을 열면 임차인이 적은 원문, 분류 결과, 접수 시각을 함께 본다. "확인 필요" 표시가 있으면 목록과 상세 모두에서 구분되어 보인다.

## 분류 값

세 축 모두 정해진 목록이며 각 축에 "기타·불명"이 있다.

- **문제 유형**: 누수 / 난방·온수 / 전기 / 곰팡이 / 배수 / 도어락·창호 / 기타
- **대상 시설**: 욕실 / 주방 / 보일러·온수기 / 현관·도어락 / 창문 / 거실·방 / 공용부 / 기타·불명
- **긴급도**: 긴급(안전 위험이나 생활 불능, 예: 가스 냄새, 전체 정전, 난방 중단) / 보통(불편하지만 당장 위험 없음) / 낮음(미관이나 경미한 불편). 이 정의는 화면에서도 확인할 수 있게 보여준다.

## 실패와 불확실한 경우

| 상황 | 동작 |
|---|---|
| 분류가 실패하거나 시간이 초과됨 | 원문은 저장하고 접수한다. 임차인에게는 접수되었다고만 알린다. 임대인 목록에는 "분류 안 됨 / 확인 필요"로 올라가고 원문이 앞에 보인다. |
| 내용이 비었거나 문제를 읽을 수 없을 만큼 짧음, 민원이 아님 | 접수하지 않고 임차인에게 어떤 문제인지 한 줄 더 적어 달라고 안내한다. 입력한 내용은 지워지지 않는다. |
| 한 메시지에 문제가 여러 개 | 한 건으로 접수한다. 가장 긴급한 문제를 기준으로 분류하고, 여러 문제가 담겼다는 표시와 "확인 필요"를 붙인다. |
| 분류에 자신이 없음 | 최선의 값을 보여주되 "확인 필요"를 붙인다. 목록에서 구분된다. |
| 어느 값도 목록에 맞지 않음 | 해당 축을 "기타·불명"으로 두고 "확인 필요"를 붙인다. |

어떤 경우에도 접수가 성립한 민원은 사라지지 않는다.

## 접근 규칙

- 접수 화면과 임대인 확인 화면 모두 로그인이 필요하다. 로그아웃 상태에서 열면 로그인 화면으로 이동한다.
- 임차인은 자기가 보낸 민원의 분류 결과만 볼 수 있고, 다른 사람의 민원은 볼 수 없다.
- 임대인은 접수된 민원 전체를 볼 수 있다. 이 슬라이스에는 물건 구분이 없으므로 "전체"는 하나의 샘플 물건 몫이다.
- 역할은 임차인과 임대인 둘이고 기본은 임차인이다. 임대인은 관리자가 지정하며, 화면에서 스스로 임대인이 될 수 없다.
- 임차인이 임대인 확인 화면을 열면 접근할 수 없다는 안내를 본다. 임대인은 접수 화면도 쓸 수 있다.

## 수용 기준

1. 로그아웃 상태에서 접수 화면과 임대인 확인 화면을 열면 각각 로그인 화면으로 이동한다.
2. 임차인이 카테고리를 고르지 않고 자연어로 "욕실 천장에서 물이 새요"를 제출하면 접수되고, 임차인은 문제 유형 누수, 대상 시설 욕실, 긴급도와 함께 분류 결과를 본다.
3. 접수 화면에는 문제 유형·긴급도·대상 시설을 고르는 입력이 없다.
4. 임시 분류기가 만든 결과임이 접수 결과와 임대인 화면에 드러난다.
5. 임대인 확인 화면의 목록은 긴급도가 높은 순이고, 같은 긴급도에서는 최근 접수가 위에 온다.
6. 임대인이 목록에서 한 건을 열면 원문, 문제 유형, 긴급도, 대상 시설, 접수 시각을 본다.
7. 분류가 실패한 민원도 원문과 함께 접수되어 임대인 목록에 "확인 필요"로 나타난다. 이 경우 임차인에게는 분류 실패가 노출되지 않고 접수 완료로 안내된다.
8. 문제를 읽을 수 없을 만큼 짧거나 비어 있으면 접수되지 않고 한 줄 더 적어 달라는 안내가 나오며, 입력한 내용이 유지된다.
9. 문제가 여러 개인 민원은 한 건으로 접수되고 여러 문제 표시와 "확인 필요"가 붙는다.
10. 분류가 불확실하거나 어느 값도 맞지 않는 민원에는 "확인 필요"가 붙고 목록과 상세에서 구분된다.
11. 임차인 계정은 다른 임차인의 민원을 목록·상세·직접 요청 어느 방법으로도 읽을 수 없다.
12. 임차인 계정으로 임대인 확인 화면을 열면 접근 불가 안내가 나오고 민원 내용은 노출되지 않는다.
13. 새로 가입한 계정은 임차인이고, 관리자가 지정하기 전에는 임대인 화면을 쓸 수 없다.
14. 새로고침하거나 서버를 다시 시작해도 접수된 민원과 분류 결과가 유지된다.
15. 접수된 민원을 한 번에 비울 수 있다(검증 반복용). 방법은 구현에서 정한다.
16. 분류 결과는 문제 유형·긴급도·대상 시설·"확인 필요"의 고정된 모양으로 만들어지고, 임시 분류기를 AI 모델로 바꿔도 화면과 저장 구조를 바꾸지 않아도 된다.
17. 접수 화면과 임대인 화면 모두 loading, empty, error, success 상태가 정상 화면과 같은 구성 문법으로 보인다. 좁은 화면에서도 입력과 주요 action이 숨겨지지 않는다.

## 범위

**이번 구현에 포함**
- 로그인한 임차인의 자연어 민원 접수와 분류 결과 확인
- 임시 분류기(키워드 규칙)와 위의 실패·불확실 처리
- 임대인 확인 화면: 긴급도 순 목록과 상세
- 임차인·임대인 역할 구분과 임차인의 본인 민원 한정 열람
- 접수 데이터의 Supabase 저장
- 접수 데이터 초기화 수단
- 임대인 목록 상단의 처리 현황 대시보드(접수=확인 전, 처리중=확인했고 해결 전, 완료=해결됨 건수). 임대인은 접수 화면을 쓰지 않으며 `/report`는 임대인을 `/landlord`로 보낸다.
- 임대인의 "확인했습니다"·"해결했습니다" 기록(시각 저장)과, 임차인이 내 접수 내역에서 임대인 확인 여부와 해결 일자를 보는 것. 확인은 한 번 기록되면 유지되고, 해결하면 확인도 함께 기록된다.

**이번 구현에서 제외**
- AI 모델 연동과 분류 품질 검증(AI로 바꾼 뒤 사용자 검증 데이터로 진행)
- 확인·해결 외의 처리 상태(진행 중 등), 수리 기록, 증빙 첨부
- 물건 구분과 임대인의 물건 소유 관계, 물건별 관리 이력 조회
- 예비 임차인의 이력 조회와 임대인에게 접근을 요청하는 흐름
- 임대인이 분류 결과를 고치는 기능
- 한 메시지를 여러 건으로 쪼개는 일
- 알림, 스팸 방지, 점수화, 가격 산정

## 설정된 제약과 이유

- 한 메시지는 한 건이다. 쪼개기는 실제 빈도를 본 뒤 정한다.
- 분류 값은 정해진 목록이다. 정렬, 필터, 검증 데이터와의 비교가 같은 값끼리 가능해야 한다.
- 접수가 최우선이다. 임차인의 신고를 잃는 것이 가장 큰 실패이므로 원문을 먼저 저장하고 분류는 그 뒤에 한다.
- 임차인의 민원 원문은 민감할 수 있으므로 로그인한 사용자 사이에서도 본인 것만 읽게 한다.
- 이 서비스는 책임 소재, 법적 과실, 보상 금액을 판정하지 않는다.

## 가정 (덮어쓸 수 있음)

- 문제를 읽을 수 없을 만큼 짧다는 기준은 구현 시 정하고, 검증하면서 조정한다.
- 목록은 긴급도 순, 같은 긴급도에서는 최근 접수 순이다.
- 임시 분류기는 키워드 규칙이며 규칙에 걸리지 않으면 "기타·불명"과 "확인 필요"가 된다.
- 한 번에 접수할 수 있는 글자 수에는 합리적인 상한이 있다.
- 샘플 물건은 하나이며 화면에서 물건을 고르지 않는다.
- 임대인은 사용자가 Supabase 대시보드에서 직접 지정한다.
- 검증용 계정은 가상의 테스트 메일로 만든다.

## 미룬 결정

- **AI 모델 선택과 연동**: 제공자와 모델은 정해지지 않았다. 대체 결정이 나올 때까지 임시 분류기가 그 자리를 맡는다(임시).
- **분류 품질 검증 방식**: 사용자가 검증 데이터를 따로 제공한다. 데이터의 형식, 정답 기준, 합격 기준은 데이터를 받은 뒤 정한다.
- **한 메시지 여러 문제의 쪼개기**: 서비스 개선 후보. 실제 발생 빈도를 보고 정한다.
- **예비 임차인의 접근 요청과 임대인 승인**: 임차를 원하는 사람이 임대인에게 접근 권한을 요청해 이력을 보는 방식. 물건 구분과 소유 관계가 정해진 뒤에 설계한다.
- **물건과 소유 관계**: 누가 어느 물건의 임대인인지.
- **임대인의 분류 수정과 세분화된 처리 상태 관리**(확인·해결 기록은 사용자 요청으로 이번 범위에 추가됨).
- **이메일 확인을 켰을 때의 가입 경로 검증**: 현재는 꺼 둔 상태로만 확인했다.

## 위험

- 임시 분류기가 분류하므로 AI 분류 품질은 이 슬라이스에서 알 수 없다. 키워드 규칙의 결과를 AI의 결과로 오해하지 않도록 화면에 임시임을 드러낸다.
- 한 메시지에 문제가 여러 개일 때 두 번째 문제가 가려질 수 있다.
- 로그인한 누구나 접수할 수 있어 스팸이나 장난 접수가 들어올 수 있다. 이번에는 막지 않는다.
- 민원 원문이 외부 DB에 쌓이므로 민감한 내용이 들어올 수 있다. 접근은 역할과 본인 기준으로 제한한다.
- 임대인을 수동으로 지정하므로 계정이 늘면 운영이 번거롭다.
- Supabase 무료 한도와 가용성은 확인하지 않았다.
- 접수 화면 자체가 검증 질문을 흐리게 할 수 있다. 접수 문장이 임대인에게 어떻게 보이는지가 실제 검증 대상이다.
